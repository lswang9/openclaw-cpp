## 1.84 WebAuthn passkeys
- real: `auth::webauthn` relying party with a minimal CBOR decoder, authData parsing and COSE keys (ES256, EdDSA/Ed25519, RS256 ≥ 2048 bits) verified through OpenSSL. Registration (`POST /login/webauthn/register/options` + `/register`) requires an authenticated principal; the passkey inherits that principal's role, and scoped tokens are refused. Passwordless login (`/login/webauthn/options` + `/login/webauthn`, public) checks clientData type, a single-use challenge (5 min), origin, rpIdHash, the UP flag, the signature and the signCount increase, then issues an HttpOnly session cookie. Removing a passkey ends its sessions. RPC `webauthn.list` / `webauthn.remove` (admin scope; forbidden for the device role). `/login/methods` reports `webauthn`. The login page gained "Sign in with a passkey" / "Register a passkey" (navigator.credentials).
- RP id/origin: `OPENCLAW_WEBAUTHN_RP_ID` / `OPENCLAW_WEBAUTHN_ORIGIN`, else derived from Host (http://). Browsers only allow WebAuthn on https or localhost.
- e2e: `e2e-webauthn.sh` (smoke): a Python software authenticator covers ES256 + Ed25519 registration and login, replay, bad signature, signCount regression, wrong origin, auth-required registration, and session end on removal.
- gaps: attestation statements are not verified (attestation "none" requested; fine for login, not for enterprise authenticator allow-lists). Passkeys are a standalone login, not combined as a second factor with token+TOTP. The browser buttons were never exercised in a real browser (no authenticator on the box).

## 1.83 Fine-grained device token scopes
- real: `pairing.link.approve {role, scopes}`. Scopes are `operator.read` | `operator.write` (also covers reads) | `operator.approvals` | `operator.pairing` | `operator.admin` | `rpc:<method-prefix>` (one RPC family; never admin methods). They are copied to the ocd_ token at claim, shown in the claim result, and re-derived on every request (cookie sessions included).
- real: enforcement. Every RPC (HTTP + WS) is checked after the role deny lists: `MethodScope` classifies methods as admin/approvals/pairing/read (status/list/get/history/…)/write, and a 403 names `required_scope`. Non-RPC HTTP: GET = read, other verbs = write, `/v1/config` = admin. Unknown scope strings are rejected at approve time. Tokens without scopes keep the old role behaviour.
- smoke: read-only token can list sessions and GET, but is refused pairing.link.list, chat.send and POST /v1/chat/completions; an `rpc:canvas.` token can call canvas.* but not tools.list; invalid scope rejected.
- gaps: scope classification is by method-name convention (last segment), not a per-method table from upstream. Agent tool calls made on behalf of a scoped device session aren't narrowed further. No scope UI on /pairing (RPC only).

## 1.82 Feishu long connection: binary pbbp2 frames
- real: `feishu_frame` protobuf codec for the larksuite SDK `pbbp2.Frame` (SeqID/LogID/service/method/headers/payload…), plus multi-part reassembly by message_id (`sum`/`seq`, any order).
- real: long-connection flow as the official SDKs do it. Endpoint discovery is `POST /callback/ws/endpoint {AppID, AppSecret}` (`locale: zh`). Binary control ping carries `service_id` from the URL query. The pong's `ClientConfig.PingInterval` reschedules pings. Data frames (`type=event`) go to the existing event handler and are acked with the same frame plus `{"code":200}` and a `biz_rt` header. The agent reply is posted with `im/v1/messages?receive_id_type=chat_id` and the tenant token (before, long-connection replies were dropped).
- e2e: `e2e-feishu-ws.sh` (smoke): an independent Python protobuf fake checks endpoint body/locale, service id, PingInterval reschedule, out-of-order 2-part event, ack, and the reply post. Self-test: codec round-trip + reassembly + truncation reject.
- gaps: never run against live Feishu/Lark (needs an enterprise self-built app). No reconnect/backoff using ReconnectCount/Interval/Nonce. Card callbacks (`type=card`) are not answered with card JSON. Payload gzip (`payload_encoding`) isn't handled.

## 1.81 ACP acpx client + audio
- real: `acp::acpx`. openclaw-cpp acts as an **ACP client**: it spawns external agents over stdio (ACP v1 newline JSON-RPC) and runs initialize → session/new → session/prompt. It collects streamed `agent_message_chunk` text and `tool_call`/`tool_call_update`, and answers the agent's `session/request_permission` (policy `deny` default | `allow_once` | `allow_always`), `fs/read_text_file` (absolute paths inside cwd only, line/limit) and `fs/write_text_file` (only with `fs_write`). `session/cancel` is sent on timeout; non-JSON stdout lines are ignored.
- real: agents. Presets `codex` (npx @zed-industries/codex-acp), `claude` (npx @zed-industries/claude-code-acp), `gemini` (`gemini --experimental-acp`), `openclaw` (own binary `acp-stdio`), and config `acp.agents.<id>.command/args`. RPC/tool callers can only pick ids, never raw argv. Entry points: RPC `acp.agents.run` (blocked for the device role), agent tool `acp_agent`, CLI `acp run --agent ID [--cwd] [--permission] [--fs-write] [--audio F] PROMPT`.
- real: audio. Prompt `audio` blocks pass through when the agent advertises `promptCapabilities.audio`; otherwise they are transcribed locally (configured STT) into text. The built-in ACP agent now accepts `audio` blocks (STT → `[Audio] Transcript:`) and advertises spec `promptCapabilities`, `agentCapabilities`, `agentInfo` and `authMethods`. It also emits `agent_message_chunk`, returns `stopReason`, and accepts protocolVersion 1 (it used to reject anything below 2, which no spec client would pass).
- e2e: `e2e-acpx.sh` (smoke): a fake agent covers deny/allow/write gating, the /etc/passwd escape refusal, tool-call status, and audio passthrough vs. local STT. There is also real interop with our own `acp-stdio`, including the agent-side transcript.
- gaps: `terminal/*` client capability not offered; no ACP `authenticate` flow for agents that require login (reported as `authMethods`/`auth_required`); one prompt per run (no persistent multi-turn acpx sessions); never run against live Codex/Claude Code/Gemini (they need their own accounts); no video.

## 1.80 Discord voice: gateway-driven join, libopus encode/decode, receive, RPC + agent tool
- real: `DiscordGateway::JoinVoice`: sends op 4 over the live connection and waits for this bot's VOICE_STATE_UPDATE (session_id) + VOICE_SERVER_UPDATE (token, endpoint). The bot user id comes from READY. Default intents now include GUILD_VOICE_STATES. Leave = op 4 with `channel_id: null`. `DISCORD_GATEWAY_URL` overrides the gateway URL.
- real: conan `opus/1.5.2`. `EncodePcm` (20 ms, 64 kbps), `DecodeOpus`, WAV read/write. Non-Ogg/WAV input (e.g. TTS mp3) goes through ffmpeg when it is on PATH.
- real: receive. After playback, `listen_ms` reads UDP, skips RTCP, decrypts, strips the encrypted header-extension body, groups by SSRC, maps SSRC→user from op 5, decodes to per-speaker WAV and optionally transcribes via the STT provider.
- real: RPC `discord.voice.{join,leave,play,status}`, plus the agent tool `discord_voice` (play `text` via TTS, or `audio_path`).
- e2e (`e2e-discord-voice.sh`, smoke): a fake main gateway + voice server. Checks the op 4 join/leave, VS1/VT handed to Identify, 50 libopus frames for 1 s of WAV, and the second speaker's 26 extension-bearing packets received and decoded (24960 samples). Self-test: Opus round-trip + extension stripping.
- gaps: no DAVE E2EE (Discord is rolling it out; if a channel requires it, sessions with `max_dave_protocol_version: 0` will be refused). Listening only happens in a window after playback; there's no always-on receiver or jitter buffer/PLC. Not exercised against live Discord (needs a bot token + voice channel).

## 1.77 Discord voice (outbound) + libcurl WebSocket fix
- real: `channels/discord_voice`: voice gateway v8 (Hello/Identify/Ready/Select Protocol/Session Description/Speaking/heartbeat with seq_ack), UDP IP discovery (74-byte), RTP framing (seq, ts+=960), `aead_aes256_gcm_rtpsize` and `aead_xchacha20_poly1305_rtpsize` (HChaCha20 RFC draft vector in self-test), Ogg Opus demux, 20 ms pacing, 5 trailing silence frames. ## 1.52 Config reload vs concurrent HTTP (exclusive lock + worker pool)
- real: `Server` holds exclusive `deps_mu_` (`std::mutex`). Request handlers and `ReloadConfigNow` serialize on it for config/tools/sessions swaps; adapter Stop/Start and the agent model/tool loop run **after** releasing the lock so reload cannot deadlock against a long run. `config.reload` RPC is handled without holding the lock across adapters.
- real: earlier `shared_mutex` + unbounded `std::thread().detach()` per HTTP client OOMed under reload hammers; HTTP is now a **bounded worker pool** (default 8, `OPENCLAW_GATEWAY_WORKERS`, queue cap 256 → HTTP 503). WebSocket upgrades still detach (long-lived).
- real: per-agent `tools::Registry` is a `shared_ptr` so in-flight agent runs keep a live registry across SetConfig rebuilds (`tools.reset()` + lazy rebuild on next Get).
- real: `scripts/e2e-config-lock.sh` (part of smoke) hammers concurrent `config.reload` + Slack inbound + `tools.list` and asserts the gateway stays healthy.
- real-sim / remaining: not a full formal proof of every deps_ field; long agent loops may still observe a mix of old tools + new config if they re-read `deps_` without the lock for the whole run. Channel credential env re-read semantics unchanged from 1.49.
